# 真机知识概念
## STM32
- STM32 是一块微控制器（MCU）芯片，也就是一块小小的嵌入式电路板。它本身不能运行 Ubuntu 和 ROS，它的工作是“硬实时”的：
1. 接收上层指令：通过串口接收来自 Jetson 的速度指令。
2. 电机控制（PID）：以极高的频率（比如 1000Hz）执行 PID 算法，控制左右轮电机的转速。Jetson 跑 ROS 时的频率只有 10-50Hz，根本来不及控制电机的高频抖动，所以必须交给 STM32。
3. 读取底层传感器：读取电机的编码器（算里程计 /odom），读取底盘上的 IMU，读取电池电压（这就是你之前查的 /PowerVoltage 的来源！）。
4. 反馈给上层：把这些底层的物理数据打包，通过串口发给 Jetson，让 ROS 知道底盘状态。
- 一句话：它是机器人的“脊髓”，负责最底层的、硬实时的反射和传感。

## 电机驱动板
- 电机驱动板是一块大功率的功率电子电路板。STM32 发出的控制信号（比如 PWM、方向电平）非常弱（通常是 3.3V 或 5V 的逻辑信号），直接接电机会烧掉 STM32，而且推不动电机。
- 电机驱动板的作用就是充当“功率放大器”和“开关”：接收 STM32 的弱电信号。从电池吸取大电流，按照信号指示，精确地把高压大电流输送给电机。控制电机的正反转和转速。
- 一句话：它是机器人的“肌肉”，接收脊髓的微弱电信号，发挥出巨大的物理力量。

## 进程与线程
- 进程（Process）：好比一家独立的餐厅。在电脑里，一个“进程”就是一个正在运行的程序，它们互相独立，互不干扰。
- 线程（Thread）：好比餐厅里的员工。线程就是“进程”内部的“员工”。它们是计算机调度的最小单位，虽然共享一个内存空间，但各自负责不同的工作流。
- 单线程（一个人干所有事）：单线程的程序，指令是一条一条排队执行的（同步执行）。只要其中一项任务卡住，整个程序就卡死不动了。
- 多线程（分工协作）：多线程允许程序同时做多件事。CPU会在多个线程之间飞速切换，让你感觉它们是同时在工作的。

## 多线程的“冲突”与“互斥锁”
- 多线程虽然好，但带来了一个新问题：共享资源冲突。
- 为了解决这个冲突，现代操作系统引入了互斥锁（Mutex），即当一个线程在使用这把锁时，其他线程需要等这个线程处理完了再上去抢，这就是多线程中的“同步”机制。 锁保证了数据不会乱，但代价是：别人得等。

## DDS：数据分发服务，是一套国际标准的通信协议。（类比成负责上门取件、打包、运输、派送的快递公司）
- 缓冲队列（Buffer Queue）：类似DDS快递公司的临时中转站。发布者把数据放进中转站里，然后订阅者接收里面的数据。但缓冲队列的容量是有上限的，由QoS里的Depth（深度）决定。
- Fast DDS（默认）：ROS2官方默认。这家公司实力强，但在无线网络下服务态度很差，动不动就把包裹卡在网点。Cyclone DDS：一家极其稳健的公司。特别擅长处理大件包裹（比如/scan），而且在局域网内速度极快。
- DDS采用的是发布/订阅（Pub/Sub）模式，负责把数据从发布者交给订阅者。
- DDS的“发现”：是整个通信链路的第一步，它的任务是让所有节点互相知道对方的存在，并协商好“用什么规则传数据”。
1. 发现的两个层次：SPDP（Simple Participant Discovery Protocol），即找人，找到网络里有哪些“参与者”（节点）；SEDP	Simple Endpoint Discovery Protocol，即找话题，找到对方有哪些发布者/订阅者。
2. 完整发现步骤（四步）
   - SPDP广播找人：每个 DDS 参与者（比如雷达驱动、SLAM）启动时，会做一件事：在自己的主网卡上，周期性地（默认每 5 秒）发送一个组播包，内容是：“我是某某节点，我的 IP 是 xxx，我的端口是 xxx，谁在？”这个组播包就是 SPDP 公告。
   - SPDP回应互相确认：当另一个节点（比如 SLAM）收到这个组播包后，它会回应一条单播消息：“我收到了，我是 SLAM，我的 IP 是 xxx，端口是 xxx，我们建立连接吧。”注意：SPDP 的“找人”用的是组播，但“回应”用的是单播。这是 DDS 设计上的一个关键优化——组播只用来“喊话”，真正的连接建立走单播。
   - SEDP交换话题信息：SPDP 找到对方后，双方会建立一条单播控制通道，然后通过这条通道交换更详细的信息：“我这里有 /scan 话题，发布者是雷达驱动，QoS 是 BEST_EFFORT。”“我这里有 /cmd_vel 话题，订阅者是底盘驱动，QoS 是 RELIABLE。”这就是 SEDP。它让双方知道具体有哪些话题可以通信、QoS 是否匹配。
   - 建立数据通道，真正开始传数据：SEDP 完成后，DDS 就知道：“SLAM 订阅了 /scan，雷达驱动发布了 /scan，两边 QoS 匹配。”于是，DDS 在两者之间建立单播数据通道（或共享内存通道），正式开始投递 /scan 数据。

## 网络通信的三大方式（底层IP协议，也是DDS分发数据的方式）
- 想象你是一个快递员（发布者），要把一份数据（比如雷达数据）送给接收者（订阅者）。
- 单播（Unicast）：“一对一”寄件。你确定收件人是谁，直接填上他的具体地址，把包裹送给他。速度快，但如果你要把同一份包裹送给100个人，你得复制100份，分别填100个地址，极其累。
- 广播（Broadcast）：“小区大喇叭”。你对着整个局域网大喊：“这里有份雷达数据，谁要谁拿！”所有的设备都能听到，但大部分不相关的设备（比如打印机、摄像头）也会被打扰，非常浪费网络带宽。
- 多播或组播（Multicast）：“建个群聊”。你把数据发到一个特定的“群聊地址”（多播组）。只有加入了群聊的设备（订阅者）才会收到这份数据。既不用复制多份，又不会打扰群外的设备。这是 ROS2/DDS 自动发现节点的核心机制。

## 快订阅者与慢订阅者
- 快订阅者：接收数据的速度大于等于发布者发布数据的速度，数据在它这里完全不积压，随接随走。
- 慢订阅者：接收数据的速度小于发布者发布数据的速度，数据在它这里会严重积压。
- SLAM、RViz2、Nav2都是慢订阅者，尤其Nav2更慢

## 反压
- 在生产者-消费者模型（或者发布者-订阅者）中，如果生产者（发布者）产生数据的速度大于消费者（接收者）处理数据的速度，或者传输通道的容量有限，就会导致缓冲区填满。此时，系统为了保证不丢数据，或者受到操作系统的限制，会迫使生产者（发布者）暂停发送（阻塞/Block），这就是“反压”。

## X11
- X11 是一套 Linux/Unix 系统用来显示图形界面的底层协议。
- 你可以把它理解成一个公司的“画图部门”。它的工作模式非常奇葩，是 C/S（客户端/服务器）架构，分为两半：
1. X Server（服务器端）：负责管理真正的硬件（显示器、键盘、鼠标）。它的任务就是：“把画面画在物理屏幕上，把鼠标键盘的操作传回去。” 它在你的真机（Jetson）系统底层跑着。
2. X Client（客户端）：你运行的图形程序，比如 RViz、浏览器、终端。它的任务是：“算好要画什么内容（比如地图、点云）。” 它通常在你的 Docker 容器里跑着。
3. 正常情况下，X Client 算好画面后，需要通过 X11 协议，把画面传给 X Server，X Server 再画到显示器上。


## 话题：/scan
- 它是激光雷达（Lidar）驱动节点把硬件采集到的物理距离数据，翻译成 ROS2 系统能听懂的标准化语言后，发布出来的最核心的传感器数据流。
- 数据类型： sensor_msgs/msg/LaserScan
- 包含数据：角度（angle_min 到 angle_max）：雷达转一圈，从 -180° 到 +180°。距离（ranges 数组）：在每个角度上，雷达测到障碍物的距离（比如 0.65米、2.3米）。时间戳（header.stamp）：这帧数据是什么时候产生的（你之前排查延迟的核心）。坐标系（header.frame_id）：这帧数据属于哪个雷达坐标系（比如 laser）。
- 发布者：镭神激光雷达节点，负责从串口（/dev/wheeltec_lidar）读取雷达原始数据，解析成 ROS2 标准的 LaserScan 消息，并发布到 /scan 话题上。
- 订阅者：slam_toolbox，负责接收 /scan 数据，结合 TF 树（里程计和位姿），通过扫描匹配算法计算出机器人在地图中的位置，并绘制地图。

## 镜像翻转
- 正常情况下，ROS机器人遵循右手坐标系：X轴朝前，Y轴朝左，Z轴朝上（以机器人为第一人称视角）。如果你原地向左转（逆时针），角速度（Yaw）应该是正数（+）。（旋转的正方向，是由右手定则决定的；伸出你的右手，大拇指指向Z轴的正方向（也就是天空）；此时，你剩下四根手指弯曲的方向，就是旋转的正方向）
- 而镜像翻转的意思是：机器人物理上向左转，但激光雷达的数据（或里程计的数据）却告诉系统“我向右转了”（你举起右手，但镜子里的你举的是左右，左右完全反了）。两者的数据在slam里打架，结果就是地图扭曲、重影、或者小车直接原地打转。

- 测试：
1. 里程计的转向符号
```
ros2 topic echo /odom --field pose.pose.orientation    #持续不断地读取并打印小车里程计中的姿态数据（四元数）。
ros2 topic pub -r 10 /cmd_vel geometry_msgs/msg/Twist "{angular: {z: 0.4}}"    #让小车向左旋转0.4弧度。
```
2. 雷达的旋向/镜像
把纸箱放在车的【左前方约 45°】，距离 1 米左右。在RViz上看箱子出现在左侧还是右侧。

## 雷达的三项关键参数（雷达三命令）
```
ros2 topic echo --once /scan --field angle_min    #起始角度（雷达开始扫描时候的角度），通常是-3.14159（-派）
ros2 topic echo --once /scan --field angle_max    #终止角度（雷达结束扫描时候的角度），通常是3.14159（+派）
ros2 topic echo --once /scan --field angle_increment    #角增量/角分辨率（雷达每转一步，角度增加了多少。也就是两个相邻激光点之间的“夹角”）。如果雷达一圈有360个点，大概是0.01745（1°）；如果一圈有720个点，大概是0.00872（0.5°）。
```

## 掩码
- 本质上就是一张“遮罩”或“过滤器”，核心作用就是两个字： “过滤”。它决定了“哪部分数据我保留，哪部分数据我丢弃”。

## 中继（relay）
- “中继”就是一个“快递中转站”。在通信系统里，如果两个节点直接通信太慢、太卡，甚至会把一方拖死，我们就会在中间加一个“中继节点”。
- 它的工作极其简单：只负责原封不动地把数据从一个地方搬到另一个地方。
- 起中继：python3 ~/relay_scan.py

## 系统性能诊断
告诉你系统开机多久了，以及过去 1、5、15 分钟的平均负载。
```
uptime
```
抓取当前系统最消耗资源的进程列表（只抓一次，不持续刷新）。
```
top -b -n1 | head -25
```
可用CPU核心数。校验uptime里的负载是否超标。
```
nproc
```
显示系统内存（RAM）和交换分区（Swap）的使用情况。输出结果中，Mem是物理内存；Swap是虚拟内存，如果 used 数值持续变大，说明物理内存不够用了。因为Jetson的SD卡/eMMC读写速度很慢，一旦开始用Swap，你的机器人就会瞬间“卡死”，/scan延迟飙高，频率暴跌。buff/cache：系统用来缓存磁盘读写的内存。通常数值很大，这是正常的，不用担心；available（最重要）：真正可用的内存。如果这个数字很小（比如小于500Mi），系统就会开始动用最后的“备胎”——Swap。

```
free -h
```

## 网络接口
- lo（Loopback，本地环回）：它不是真实的物理网卡，而是 Linux 系统内部虚拟出来的一条“无限宽、无限快”的走廊。数据根本不经过任何硬件，直接在内存里传。速度极快（微秒级），没有任何丢包。Docker 容器内部、容器与真机系统之间的所有本地通信，都应该走这扇门。 比如雷达驱动发给 SLAM、ros1_bridge 转发数据，如果走 lo，延迟可以忽略不计。
- wlan0（Wireless LAN，无线网卡）：是Jetson上的物理无线网卡。速度极度受限。 极易受到干扰、带宽窄（可能只有几MB/s），且延迟极高（毫秒级甚至几百毫秒）。这扇门只应该留给你的虚拟机 RViz 使用。本机的雷达和 SLAM 之间的数据传输，绝对不该走这扇门！
- eth0（Ethernet，有线网卡）：是Jetson 上的物理有线网口，稳定、带宽大（千兆）、延迟低。


# 问题与反思
## 平凡替身实验
- 用最笨的假节点，即平凡替身，替换掉可疑部件，只要平凡替身复现了症状，病灶就在你替身掉的那一层之下。此时任何留在原层的调整都是浪费时间。
- 本次是针对/scan延迟增加和掉频的问题，引入了假发布者与反订阅者。
1. 假发布者是一个纯 Python 脚本，它没有任何复杂的算法，没有串口读取，没有 C++ 的互斥锁，只是单纯地以 12Hz 的固定频率往 DDS 里扔 1667 个点。
2. 哑订阅者更极端，它订阅了数据但立刻扔进垃圾桶（> /dev/null），不做任何计算。
3. 说明的问题：如果连这种“极简的无脑程序”加上一个“只看不做的哑巴订阅者”都会导致掉频，那就证明了问题既不在 SLAM 算法，也不在 CPU 算力，更不在雷达驱动的 C++ 代码里，传输层（DDS + 网络接口）才是罪魁祸首。

## 单变量原则
一次只改一个变量，改完立刻验证。 否则你永远不知道是哪一条起了作用。

## 差分测量
1. 同一个 ros2 topic delay /scan，在容器里跑和在虚拟机里跑，含义完全不同：
   - 容器内正常、VM 侧异常 → 病在网络/中间件
   - 容器内也异常 → 病在本地链路或算力
2. 跨层系统里，同一个指标必须在两端各测一次，差值才是信息。

## 改了没效果"要分三种情况，别混为一谈
1. 参数没生效（配置没加载、没重启节点、daemon 没刷新）
2. 参数生效了，但它不是瓶颈（do_loop_closing 之于传输延迟）
3. 瓶颈根本不在这一层（你改了整整一周的 SLAM 参数，属于这一种）
- 你记录里"均无效"三个字背后，其实是三种完全不同的失败，它们的下一步动作截然相反。
